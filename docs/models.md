# The case and disc models

Jawon's jewel case and CD are **generated by a committed Blender script**, not
modelled by hand and not downloaded.

- Source: `tools/models/build_models.py`
- Output: `app/src/main/assets/models/{case_tray,case_lid,case_closed,disc,pocket}.glb` and the props

| model | used by | tris | notes |
|---|---|---|---|
| `case_tray` | the held case | 2176 | well, spindle rosette, hinge knuckles |
| `case_lid` | the held case | 708 | origin on the hinge axis |
| `case_closed` | the wall | 768 | shelved frame, opaque |
| `disc` | the held case | 4608 | 1.2mm thick, radial UVs |
| `pocket` | the iPod mode's device | 6958 | seven objects, one per material; life size, 61.8 × 103.5 × 10.5mm |

**Why the shelf gets its own case.** A shut jewel case shows none of the tray's
interior, and the wall draws up to ~470 at once — carrying that interior would
be over a million triangles rendering nothing. `case_closed` is also modelled in
the *shelved* frame (X thickness, Z depth, spine at +Z) rather than the held
one, so `CaseSlots` needs no rotation and the art-plate positions tuned against
those axes keep working.

It is opaque, where the held case's lid is transparent. The wall used to hang a
thin transparent panel off every slot for the plastic sheen; clearcoat is that
sheen as a second specular lobe on an opaque surface, so hundreds of blended,
depth-sorted draws became none.

Both the script and its output are committed, for the same reason
`dust.filamat` is: nothing in the Gradle build can produce them, and a clone
should not need Blender installed to build the app.

## Regenerating

```
blender --background --factory-startup --python tools/models/build_models.py
```

Run from the repository root — output paths are relative to it. Built against
Blender 5.1; the script only uses `bmesh`, modifiers and the glTF exporter, all
of which are stable API.

**Edit the script, never the `.glb`.** There is no `.blend` in the tree, and a
hand-edit to the exported file is lost the next time anyone runs the script.

### `disc.glb` is not byte-reproducible

The three case models hash identically across runs. `disc.glb` does not — every
rebuild produces a different hash, and a slightly different vertex count
(~3360–3380 for the same geometry).

It is the only model built through a `Solidify` modifier and the only one
exporting tangents, and Blender evaluates that stack across threads, so vertex
values come out bit-different run to run and the exporter's vertex dedup then
merges a different number of them. Bounds, triangle count and appearance are
unaffected.

Two things this is **not**, both checked: the embedded placeholder PNG (its
bufferView is byte-identical since the pixel buffer is written explicitly), and
the bevel's overlap clamping (lowering the width well below the threshold
changed nothing).

Practical consequence: regenerating the models dirties `disc.glb` even when
nothing about the disc changed. That diff is safe to discard. Fixing it properly
means building the disc's ring, rim and thickness directly in `bmesh` instead of
letting `Solidify` do it — worth doing if the disc is ever reworked, not worth
destabilising working geometry for on its own.

## Why a script rather than a .blend or a bought model

ENGINEERING.md originally locked geometry to "procedural, no downloaded models"; M11
moved it to imported glTF on the owner's call. This is both, and that is the
point rather than a compromise:

- **Parametric.** Every dimension is a named constant that must agree with
  `WallDimens`. Change the case thickness in one place and the model follows.
- **Reviewable.** A geometry change shows up as a readable diff.
- **No licence.** Nothing to attribute, nothing to re-check before shipping.
- **Tessellation is ours.** Disc segment count and bevel width are variables,
  which is what M10's GPU tiers will want.
- **Real bevels and correct shading normals**, which is the part hand-written
  vertex buffers were never going to give cheaply — and the reason the old
  geometry read as computer graphics. A perfect 90° corner catches no specular
  highlight; `BEVEL_W` is 0.35mm, about what a moulded polystyrene edge is.
- **Materials the stock pipeline cannot express.** The exporter writes
  `KHR_materials_clearcoat`, which gltfio understands and SceneView's stock
  materials have no parameter for at all. See `materials.md`.

A survey of available jewel-case models found none that fit: the free ones are
plain low-poly with no PBR, and the one with genuine 2K PBR textures hides its
open/close rig in a C4D file and exports no glTF. All of them would have needed
Blender work anyway to split the lid, rebuild the hinge pivot, and re-UV for
swappable artwork — which is most of the work, without control of the result.

## Traps, all of which have already bitten

### The thickness axis is negated on export

The exporter's Y-up conversion maps Blender `(x, y, z)` → glTF `(x, z, -y)`.
The case's thickness therefore **flips sign**: the front of the case, at app
`+Z`, is at Blender `-Y`.

The first `build_tray()` ignored this and computed its front and back faces as
though Blender Y were app Z. Everything still exported, still loaded, still
rendered — as a tray mirrored through the case's mid-plane, sitting in the
lid's half with its well facing away from the camera. On screen it was a
featureless slab, which looks like a lighting bug and is not one.

Use the `az()` helper for every thickness coordinate and think in app Z.

### The lid's origin is the hinge axis

Not the lid's centre. `ActiveCase.kt` hangs the lid off a bare `Node` at the
hinge and swings that node 123°, so the mesh has to share that origin for the
pivot to be right. A self-centred lid swings about its middle — which reads as
an animation bug and is a modelling one.

Its exported X bounds start at 0 for exactly this reason; that is the check.

### A material with no texture compiles a shader that cannot sample one

gltfio picks a material variant per glTF material, keyed on which texture slots
that material declares, and signals "none here" with `baseColorIndex = -1`. A
disc exported without a `baseColorTexture` therefore yields a shader that never
samples — and the app's album art would have nowhere to bind, silently, with the
disc rendering flat and nothing in the log to explain it.

Hence `attach_placeholder_basecolor()`: an 8×8 white image whose only job is to
make the slot exist. `WallSceneScreen` swaps the real artwork in at runtime with
`setParameter("baseColorMap", …)` on the model's own material — **not** by
replacing the material, which would throw the clearcoat away with it.

### Booleans on millimetre features

The tray is a floor plus four walls, not a solid block with a well cut out.
Booleans on features this small leave degenerate slivers that the bevel modifier
then explodes. The disc's annulus is likewise two bridged edge loops rather than
a hole subtracted from a cylinder — the first attempt built the inner cylinder
*and* subtracted it, leaving a self-intersecting mesh and "Mesh disc is not
valid" from the exporter.

### Tangents need triangles

The exporter derives tangents from the mesh and gives up on n-gons, warning
"Could not calculate tangents". `finish()` adds a Triangulate modifier after the
bevel for this reason.

## Verifying a change

The exported POSITION accessor's `min`/`max` are the cheapest real check, since
they are in final glTF/app coordinates:

| file | expected bounds |
|---|---|
| `case_tray.glb` | X ±0.063, Y ±0.071, **Z −0.0050 … +0.0013** (back half) |
| `case_lid.glb` | **X 0 … +0.125** (hinge origin), Y ±0.071, Z −0.0022 … +0.0040 |
| `case_closed.glb` | **X ±0.005** (thickness), Y ±0.071, **Z ±0.0625** (depth) |
| `disc.glb` | X/Y ±0.060, Z ±0.0006 (1.2mm thick) |
| `pocket.glb` | X ±0.0309, Y ±0.0518, **Z −0.00525 … +0.00525** (10.5mm), and per part: the wheel's front face at **+0.00465** (0.6mm inside the plate's +0.00525) and the button's at **+0.0047**. Nothing in `pocket_details` may pass ±0.0518 in Y — the jack, the hold switch and the connector are sunk into those edges, not stuck on them. |

Note `case_closed`'s axes are the odd ones out, and deliberately: it is the only
model in the shelved frame, so its X is the 10mm edge rather than the 125mm
cover. A closed case whose X spans ±0.0625 has been built in the held frame by
mistake.

A tray whose Z straddles zero, or a lid whose X is centred on zero, is the axis
trap or the origin trap respectively.

**A wheel that is proud of its plate is the same class of error**, and the bounds
caught it: the pocket player's wheel first exported at Z +0.0037…+0.0050, standing
0.7mm out of a face it is meant to sit 0.6mm inside, because `SOLIDIFY` with
`offset = +1` thickens toward the surface normal. Every recessed part on that device
is a bounds check away from being a proud one.

## Looking at a model without a phone

```
blender --background --factory-startup --python tools/models/preview_model.py \
    -- pocket.glb out.png [--angle three-quarter|front|back] [--samples 128] [--clay]
```

It re-imports the exported `.glb` — so what is judged is the file the app loads — puts
it in a small three-light studio and path-traces it. Bounds and triangle counts print
per object on the way through, in app axes.

**`--clay` first whenever a render looks wrong.** It replaces every material with one
matte grey, which separates "the geometry is wrong" from "the material is wrong". Both
of the pocket player's first-pass faults were found that way in seconds.

This is Cycles, not Filament: no room IBL, no Filament tonemapper, no post. It answers
*is the object right*, never *is the shot right*.

### Hardening normals on a flat panel

`finish(..., harden=True)` sets the bevel modifier's `harden_normals`. **Reach for it on
any large flat panel with a small bevel.** Without it the bevel's 45° faces are averaged
into the vertex normals right around the panel's edge, and since a filled face can be one
enormous triangle fan, that tilt is interpolated across the whole panel: the pocket
player's 1.1mm front plate rendered as a deep sloping tray. It reads as a modelling
mistake and is a shading one — the geometry was flat the whole time.

### A face with holes, without booleans

The front plate is a planar outline containing its own holes — the rounded rectangle, the
screen window, the wheel circle — filled with `bmesh.ops.triangle_fill` and then extruded
once, so the hole rims become the window's and the recess's walls. `docs/models.md`'s
boolean warning above is why: a 1.1mm plate is exactly the thickness that leaves slivers
for the bevel to explode.

## `disc_shards.glb` — the disc, cracked

Eight wedges, one object each, for the deletion animation. Built by
`build_disc_shards()` alongside the others.

**They use `build_disc`'s UV formula verbatim.** That is the whole reason the
shards are generated here rather than faked in the app by scaling copies of the
disc: an album's already-baked disc texture lands on the pieces with the artwork
*continuous across the cracks*. Change the disc's UV convention and this must
change with it, or the picture will tear along the breaks.

They are also the disc *before* it breaks — at rest the eight wedges sit exactly
where a whole disc would, so the app shows the same nodes sliding out as one disc
and then coming apart. There is no separate whole-disc model in the discard.

- One object per shard, because each has to move independently. A single mesh
  with disconnected islands exports as one node and can only move as one piece.
- Cuts run hub to rim, because that is where a real CD cracks — the centre hole
  is the stress concentrator.
- Cut positions and the cut lines themselves are jittered from a **fixed seed**.
  Eight even wedges read as a pie chart; a fixed seed keeps the build
  reproducible and means an album always breaks the same way.
- `SHARD_COUNT` here must match `CaseDiscard.SHARDS` in the app.
